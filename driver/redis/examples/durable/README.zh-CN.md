# 应用层持久化准入示例

此示例显式选择静态调用方策略路径（AllowStaticOnce/Rule），便于固定版本规则与持久化恢复；不是默认动态准入快速开始。默认路径应先发布 UpdateQuotas，再提交名称/cost Charge。

本示例在 Pacelock 外部管理单机、单次业务 attempt 的恢复，不新增 SDK 执行接口。
完整命令见 [英文说明](README.md#run-against-disposable-redis)：构建后分别演示正常执行、
丢失准入响应和丢失上游完成结果。每个场景使用新目录；故障命令预期返回非零。
上游只是打印消息的 mock，故障注入是边界处受控退出，不是真实网络中断。

状态依次为 prepared → admitting → admitted → executing → done。
拒绝为 denied，确定未扣减的错误为 not_charged，两者均为终态。
`recover` 只查询准入，绝不执行上游。只有独占持久化日志证明尚未进入 executing，
恢复到 admitted 后的显式 `run` 才可执行；仅凭 Replayed 或查询到 Allowed 不足以再次执行。
进入 executing 后，无论是否实际发出上游调用，都停止自动重试并要求业务对账。
因此不保证跨本地文件、Redis 和上游的 exactly-once，也不保证未知状态自动推进。

记录缺失、损坏和恢复窗口过期均保留不确定性；拒绝 ID 的决策不会改变，RetryAfter
是原始观测，查询不续期。不删除 Redis 状态、不退款、不复用过期 ID。
只有业务确认是真正的新尝试，才在新目录执行 `new`；不能覆盖旧日志。
恢复窗口保守地从本地创建时起算十分钟，因此依赖时钟稳定。

日志通过临时文件、文件同步、原子重命名、目录同步保存。目录锁只适用于可信本地文件系统
上的单机协作进程；多主机、网络文件系统、磁盘丢失、日志回滚和不支持目录同步的平台不在保证内。
真实进程被杀会遗留 lock/：操作员必须先确认原进程停止，再用 rmdir 删除空锁目录，
然后 status/recover，不能自动抢锁、删除日志或复制日志生成新尝试。
真实主机崩溃与上游失败仍需部署验证。

规则由可信、带版本的代码按账号/模型/租户顺序完整组装，测试验证每个额度和成本。
CLI 参数只是模拟可信输入；实际服务应从认证获取租户、从可靠分词获取已知输入成本。
输出未知用量、缓存 token 口径及预留/校正仍是设计提案；GCRA 不等同任意供应商分钟窗口。
版本 1 必须在旧 attempt 存续时继续可用；策略变更需要协调实例与活跃债务，改名或换 ID
不能无缝迁移债务。未知策略版本被拒绝，保留日志供人工处理。
